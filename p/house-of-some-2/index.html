House of Some 2 是独立的一条 IO_FILE 利用链，主要关注的函数是_IO_wfile_jumps_maybe_mmap中的_IO_wfile_underflow_maybe_mmap

利用条件为

  1. 已知 libc 地址
  2. 可控地址 (可写入 fake file)
  3. 可控 stdout 指针或者_IO_2_1_stdout_结构体
  4. 程序具有 printf 或者 puts 输出函数

优点如下

  1. 与 House of Some 一样可以绕过目前的 vtable 检查
  2. printf 和 puts 比较普遍，适用性广
  3. 可以在栈上劫持控制流，衔接 House of Some，完成最后攻击

前置知识#

首先我们先关注_IO_wfile_underflow_maybe_mmap函数

这个函数最后调用了_wide_data内的虚表_IO_WUNDERFLOW

那么继续深入_IO_file_underflow_maybe_mmap函数

这个函数最后调用了 FILE 的虚表_IO_UNDERFLOW

继续深入decide_maybe_mmap函数

这个函数有一个关键的_IO_SYSSTAT调用，以及，在这个函数最后会恢复 FILE 和_wide_data的虚表

整理一下可以知道，如果一个 FILE 进入了函数_IO_wfile_underflow_maybe_mmap，那么他将会运行如下的流程

  2. decide_maybe_mmap 函数结束，恢复两个虚表
  3. _IO_UNDERFLOW (fp)调用虚表
  4. _IO_WUNDERFLOW (fp)调用虚表

这个时候就能衍生出一个大胆的想法，如果我们先将栈复制一份到可控的区域，再通过偏移写入，最后再拷贝回到栈内，那么我们就能完美的绕过 canary 并且，并不需要泄露 canary

House of Some 2 is a standalone IO_FILE exploitation chain. The function we mainly focus on is _IO_wfile_underflow_maybe_mmap in _IO_wfile_jumps_maybe_mmap.

The exploitation requirements are:

  1. Known libc address
  2. A controllable address (where a fake file can be written)
  3. Controllable stdout pointer or the _IO_2_1_stdout_ structure
  4. The program has an output function such as printf or puts

The advantages are:

  1. Like House of Some, it can bypass the current vtable checks
  2. printf and puts are very common, so it has broad applicability
  3. It can hijack the control flow on the stack, chaining into House of Some to finish the final attack

Continuing into the decide_maybe_mmap function

This function has a key _IO_SYSSTAT call, and at the end of this function, the vtables of FILE and _wide_data are restored.

Putting it all together, if a FILE enters the _IO_wfile_underflow_maybe_mmap function, it will go through the following flow:

  1. _IO_SYSSTAT(fp, &st) calls a vtable entry, passing in a stack pointer
  2. The decide_maybe_mmap function finishes, restoring both vtables
  3. _IO_UNDERFLOW (fp) calls a vtable entry

Controlling rdx#

Unfortunately, in the above function flow there is nothing that manipulates rdx (note: using Ubuntu GLIBC 2.35-0ubuntu3.1 as the example, the same applies below).

The only thing we can control is the _IO_SYSREAD (fp, fp->_IO_buf_base,fp->_IO_buf_end - fp->_IO_buf_base); in the later _IO_UNDERFLOW (fp) call. Since decide_maybe_mmap forcibly restores the vtables, we don’t need to worry about the effects of tampering with the vtables here.

What happens if rdx is uncontrollable and we directly execute write(fp, &st, ??)? It returns 0 or non-zero.

So back to decide_maybe_mmap

This checks the return value: if _IO_SYSSTAT (fp, &st) returns 0, the if body is skipped right away; if it returns non-zero, let’s look at the definition of S_ISREG

We don’t need to care about the exact values; we can see the final check uses an == comparison. Given the limitations of the data on the stack, the probability of passing this check is low.

There is also the st.st_size != 0 check. Without stat logic executing correctly and the stack remaining in its original state, the probability of this if passing is low.

If it is still likely to pass, we can just make fp->_offset == _IO_pos_BAD || fp->_offset <= st.st_size false.

Then decide_maybe_mmap can complete smoothly, and the contents of the forged fp remain completely unchanged.

Unfortunately, the decide_maybe_mmap function is compiled with a canary, so we cannot complete the stack overflow without leaking the stack.

Because of the fileno setting, we cannot perform write(1, stack, rdx) either. Is there really no way?
