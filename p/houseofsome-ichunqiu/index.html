简单的分析#

通过逆向可以知道，这里泄露 libc 是通过 scanf 的未写入 trick 实现的，但是 ida 观察 init 函数的时候，并不能发现 stdin 等数据放到了栈上，需要 gdb 观察或者阅读汇编才知道。

其次，这里有一次 libc 内任意地址写 \x00 的机会在 draw 功能

还有一个小 trick——fopen，这个函数会使用 malloc 分配一个 IO_FILE_plus 结构，作为打开文件的管理块，并通过头插法进入 IO_list_all

总结一下

  1. 已知 Libc 地址
  2. 一次 libc 内任意地址写 1 字节 \x00，off by null
  3. fopen 能使得 IO_list_all 内写入 heap 地址
  4. 由于 wide_data 的 vtable 加入了 check，故不能使用 apple2 的链条

House of Some#

详细的原理见https://blog.csome.cc/p/house-of-some/

其使用的方法是

  1. 已知 glibc 基地址
  2. 可控的已知地址（可写入内容构造 fake file）
  3. 需要一次 libc 内任意地址写可控地址
  4. 程序能正常退出或者通过 exit () 退出

其中，条件 1 和 4 程序中可以直接满足，条件 3 可以通过 fopen 和一次 off by null 完成，条件 2 可以被弱化，并不需要已知，只需要可控即可

那么在构造任意地址写的 fake_file 的过程中，需要 wide_data 指针，这个指针需要在可控地址位置 —— 堆内，但是我们并不能泄露堆地址

这里需要使用 largebin 的 next size 指针残留，构造出一个合法的 wide_data 地址

PS：这里可以运用https://enllus1on.github.io/2024/01/22/new-read-write-primitive-in-glibc-2-38/#more，改进后就不需要 wide_data 了

A Quick Analysis#

From reversing, we can see that the libc leak here is achieved via the scanf-not-writing trick. However, when inspecting the init function in IDA, you can’t tell that values like stdin are placed on the stack — you need to observe it with gdb or read the assembly to figure that out.

Second, the draw function gives us a one-time chance to write \x00 to an arbitrary address within libc

There is also a small trick — fopen. This function uses malloc to allocate an IO_FILE_plus structure as the control block for the opened file, and inserts it at the head of IO_list_all

To summarize

  1. The libc address is known
  2. One arbitrary 1-byte \x00 write within libc, i.e. off by null
  3. fopen can write a heap address into IO_list_all
  4. Since a check was added for the wide_data vtable, the apple2 chain cannot be used

House of Some#

For the detailed principle, see https://blog.csome.cc/p/house-of-some/

The method requires

  1. The glibc base address is known
  2. A controllable, known address (where you can write a fake file)
  3. One arbitrary write of a controllable address within libc
  4. The program can exit normally or via exit()

Among these, conditions 1 and 4 are directly satisfied by the program; condition 3 can be achieved through fopen plus a single off by null; and condition 2 can be weakened — the address doesn’t need to be known, only controllable

So when crafting the fake_file for the arbitrary write, we need a wide_data pointer, and that pointer must point to a controllable location — inside the heap. However, we cannot leak a heap address

Here we need to exploit the residual nextsize pointer of a largebin chunk to construct a valid wide_data address

PS: You can also use https://enllus1on.github.io/2024/01/22/new-read-write-primitive-in-glibc-2-38/#more — with that improvement, wide_data is no longer needed

Afterthoughts#

I was a bit careless when designing the challenge — I forgot that main_arena is also inside libc, which made it possible to modify the TopChunk via off by null and ultimately control the heap layout

That approach is fairly complex though, so it was a small unintended solution. The challenge was released with more than 30 hours remaining in the competition, got its first blood 14 hours later, and ended with only 5 solves — which is within my expectations
